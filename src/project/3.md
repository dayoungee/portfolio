# 📌Summary

### 코드 스테이츠에서 진행한 Pre Project로 개발자 커뮤니티 페이지인 Stack Overflow를 클론 코딩하였습니다. 해당 팀에서 팀장을 맡아 팀원들을 이끌어 프로젝트를 진행하였습니다.

### 백엔드 팀에서는 User, Question, Answer 도메인을 나누어 역할을 분담하였습니다. 제가 담당했던 업무는 Question 쪽이었습니다.

### CI/CD로 들어만 보았던 Jenkins를 활용하고, 테스트 서버를 직접 구축한 경험으로 해당 프로젝트를 통해 배포 관련 경험을 쌓을 수 있어 의미있는 프로젝트였습니다.

<br>

### 주요기능

- #### 회원가입, 로그인, 로그아웃, 회원 탈퇴
- #### 질문 작성, 삭제, 수정
- #### 답변 작성, 삭제, 수정
- #### 해당 질문, 답변에 추천, 비추천(API만 구현)
- #### 질문 목록 페이지네이션 적용(작성일자 기준으로 정렬 가능)

# 🔍Meaning

### 프로젝트 시작 전, 테스트 서버는 당연하게 있어야 한다 생각했습니다. 때문에 직접 테스트 서버를 개발 전에 EC2를 활용하여 구성하였습니다. 해당 기관에서 깃허브 액션을 학습했지만, 기관에서 제공해준 GitHub Repository에서는 깃허브 액션을 사용할 수 없는 환경이었습니다. 깃허브 액션을 사용하겠다면, 본인 리포지토리로 Fork하여 사용해야했습니다. 이는 불편한 방법이라 생각해 공용 리포지토리에서 CI/CD를 구성할 수 있는 방법을 모색했습니다.그렇게 해서 찾은 방법이 Jenkins를 적용하는 방법이었습니다. EC2서버에 Jenkins를 설치하여 CI/CD 서버를 구축해 그 이후, 수동적인 배포 작업없이 편안한 환경에서 개발할 수 있었습니다.

### 프로젝트를 진행하면서 프론트에 API 문서를 제공해야 했기 때문에 Spring Rest Docs와 Swagger 중에서 어떤 것을 도입할지 고민해야 했습니다. 테스트 코드를 강제하는 Spring Rest Docs를 선택하고 싶었지만, 프론트에서도 쉽게 테스트가 가능한 Swagger의 장점을 포기할 수 없었습니다. 그러던 와중 Spring Rest Docs의 테스트 코드를 활용하여 OpenAPI(Swagger 3.0)의 결과를 만들어주는 라이브러리를 찾아 이를 적용했습니다.적용 결과 Spring Rest Docs의 테스트 코드를 작성하여 Swagger UI를 제공해줄 수 있었습니다. 물론 Swagger에서 테스트도 가능했습니다.

### Spring Rest Docs 테스트 코드를 작성해야했기 때문에 테스트 코드는 강제된 상태였습니다. Spring Security를 적용 후, 테스트 코드에서는 당연하게도 불통과가 발생됐고, 이를 리팩토링 하는 과정에서 따로 JWT를 발급하여 이를 헤더에 실어서 보내는 방법으로 해결할 수 있었습니다. WithMockUser 애노테이션을 통해 해결할 수 있겠지만, 해당 방법을 적용함으로써 Swagger의 authroize button을 활성화 할 수 있어 Swagger에서 인증이 필요한 API도 테스트가 가능했습니다.

### 해당 프로젝트를 통해 테스트 코드 작성법과 서버 환경 구성에 대해 공부할 수 있어 뜻 깊은 시간을 보냈습니다.
