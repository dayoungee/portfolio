# 📌Summary

### 코드 스테이츠에서 진행한 Pre Project로, 개발자 커뮤니티 페이지인 Stack Overflow를 클론 코딩하였습니다. 이 프로젝트에서 저는 팀장을 맡아 팀원들을 이끌어 프로젝트를 진행하였습니다.

### 백엔드 팀은 User, Question, Answer 도메인을 나누어 역할을 분담했는데, 제가 담당했던 부분은 Question 기능 개발이었습니다.

### 또한, CI/CD로 들어만 보았던 Jenkins를 활용하여 테스트 서버를 직접 구축한 경험을 쌓아 해당 프로젝트를 통해 배포 관련 역량을 크게 향상 시킬 수 있었습니다. 그렇기 때문에 이 프로젝트는 제게 의미있고 가치있는 프로젝트였습니다.

# 🔍Meaning

### 프로젝트를 시작하기 전, 테스트 서버부터 구축해야 한다는 생각에 직접 EC2를 활용하여 테스트 서버를 구성했습니다. 처음에는 기관에서 제공해준 GitHub Repository(공용 리포지토리)에서 깃허브 액션을 사용하려고 했지만, 환경적인 제약으로 인해 깃허브 액션을 사용할 수 없었습니다. 그래서 공용 리포지토리에서 CI/CD를 구성할 수 있는 방법을 모색하게 되었습니다. 그 결과 Jenkins를 적용하여 EC2 서버에 CI/CD 환경을 구축했고, 이후로 수동적인 배포 작업 없이 편안한 환경에서 개발할 수 있었습니다.

### 프로젝트 진행 중, API 문서를 프론트에 제공해야 했습니다. 이때, Spring Rest Docs와 Swagger 중에서 선택에 어려움을 겪었습니다. 테스트 코드를 강제하는 Spring Rest Docs의 장점을 포기하기 어려웠지만, 프론트에서도 쉽게 테스트할 수 있는 Swagger의 이점을 놓칠 순 없었습니다. 그러던 중 Spring Rest Docs의 테스트 코드를 활용하여 Swagger UI를 제공하는 방법을 찾아냈습니다. 이렇게 함으로써 Swagger UI를 제공하면서 Spring Rest Docs의 테스트 코드를 작성할 수 있었고, Swagger에서도 테스트가 가능했습니다. 이렇개 Spring Rest Docs와 Swagger UI를 섞어 사용할 수 있는 이유는 Spring Rest Docs로 작성한 테스트 코드를 OpenAPI3 Spec으로 변환시키고, 변환 된 OpenApi3 Spec을 Swagger UI로 생성해주도록 설정하였기에 가능했습니다.

### Spring Rest Docs로 인해 테스트 코드를 작성해야했기 때문에 테스트 코드는 강제된 상태였습니다. Spring Security를 적용 후, 테스트 코드에서는 당연하게도 불통과가 발생했습니다. 이를 해결하기 위해 테스트용 JWT를 발급하여 이를 헤더에 실어서 보내는 방법으로 해결할 수 있었습니다. WithMockUser 애노테이션을 통해 해결할 수 있겠지만, 앞서 말한 테스트용 토큰 발급 방법을 적용함으로써 Swagger의 authorize 버튼을 활성화하여 Swagger에서 인증이 필요한 API도 테스트할 수 있었습니다.

### 이 프로젝트를 통해 팀 리더로서의 역량을 발휘하고 배워가는 것은 물론, 테스트 코드 작성법과 서버 환경 구성에 대해 깊이 있는 학습을 할 수 있어 기술적인 측면에서도 경험을 쌓을 수 있었습니다. 더불어 프론트 포지션과 협업을 하는 것은 처음이었기 때문에 각각 다른 포지션과의 협업과 소통을 통해 효과적인 팀워크를 구현하는 방법을 배우게 되었습니다. 이러한 성과들과 의미있는 경험들을 바탕으로 미래에도 더 큰 프로젝트를 성공적으로 이끌어나가고 싶다는 생각을 했습니다.
